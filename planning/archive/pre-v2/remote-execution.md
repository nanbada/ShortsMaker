# Muse VM·Claude/GPT 실행 설계

> 상태: v2 이전 VM 우선 설계 이력. [기획 v2](../../2026-10-04-claude-code-render-plan-v2.md)에서 Mac 우선·VM 선택으로 대체되었다. 아래 설치·큐·배포 절차는 현재 실행 지시가 아니다. 저장소·VM 정보도 당시 관측이며 현재 로컬 상태는 [README](../../../README.md)를 따른다.

2026-10-04 개정. 상태: 설계, 미구현. 사용자 확인: Muse AI VM에 Claude/GPT CLI 연결, **구독 로그인** 사용. VM OS·CPU/RAM·영속 저장·상시 가동·CLI 제품/버전·남은 사용 한도는 미확인이다.

## 1. 선택: 기존 VM에서 제작을 완료하는 단일 워커

추천 기본 구조는 `VM 예약 실행 → 단일 제작 워커 → Claude/GPT CLI → 확정 음성·VideoSpec → VM 렌더 → 검수용 결과`다. AI 추론은 Claude/OpenAI 서비스가 수행하고, VM은 CLI·파일·브라우저·인코더를 실행한다. VM을 쓴다는 이유로 로컬 LLM 가중치나 GPU가 필수가 되지는 않는다. 실제 렌더 자원은 장면·엔진별로 시험한다.

| 대안 | 장점 | 비용·실패 요소 | 선택 |
|---|---|---|---|
| Muse VM에 제작·렌더 통합 | Mac 전원과 분리, 큐·파일·실행 환경 한 곳 | VM 상시성·디스크·렌더 자원 검증 필요 | **기본안** |
| Muse VM 기획 + Mac 렌더 | 기존 M3 성능 활용 | 파일 전송·임대·Mac 수면·두 환경 관리 | VM 렌더 시험 미달 시 |
| Mac에서 구독 CLI·렌더 | 분산 전송 불필요 | 개인 장비 가동·수면 의존 | VM 영속성/접근 조건 미달 시 |
| 새 API 중심 클라우드 서비스 | 요청 단위 계측·서비스 운영 통합 | API·호스팅 추가 비용, 신규 인증·개발 | 현재 규모에선 보류 |
| 자체 로컬 LLM 중심 | 외부 추론 호출 없음 | 모델 설치·품질 검수·하드웨어 운영 | 명확한 필요가 생길 때 |

하루 1~3편에는 별도 분산 에이전트 플랫폼을 추가하지 않는다. 두 AI가 서로 계속 지시하는 구조도 쓰지 않는다. 큐·예산·최대 횟수·타임아웃은 일반 코드가 통제한다.

## 2. Claude와 GPT 역할

| 작업 | 기본 담당 | 호출 정책 |
|---|---|---|
| 근거 묶음 → 영어 대본·컷 의도·화면 문구 | Claude CLI | 편당 작성 1회 |
| 구조·길이·수치 원문 일치 검사 | 일반 코드 | LLM 없이 매번 |
| 불명확한 주장·새로운 포맷·품질 점검 | GPT CLI | 조건부 1회, 오류 필드만 반환 |
| 수정 | 최초 작성 모델 | 필요한 경우 1회, 전체 재작성 대신 관련 필드 수정 |
| 템플릿·렌더러 개발과 오류 수정 | GPT/Codex 또는 Claude 개발 세션 | 운영 큐 밖, 변경 검증 후 릴리스 |
| 자막·영상 렌더·파일 검증 | 일반 코드 | AI 호출 없음 |

이는 운영 편의를 위한 초기 역할 배정이며 Claude의 글쓰기 또는 GPT의 검증 능력이 항상 우위라는 주장이 아니다. 동일한 대표 대본 10개로 근거 정확성·JSON 통과·수정 횟수·실행 시간·구독 한도 소비를 비교하고 필요하면 기본 담당을 바꾼다. GPT의 동의도 원문 사실 검증을 대체하지 않는다. 매 영상의 이중 호출은 기본이 아니다.

기본 모델·추론 강도는 VM의 native 설정과 프로젝트 실행 프로필에 기록한다. 문장 지시로 모델을 바꾸지 않는다. 정확한 모델 ID·버전은 설치 환경에서 확인해 고정하며 `latest` 자동 변경은 쓰지 않는다. 제한된 단계의 일상 생성에는 낮은 추론 설정부터 시험하고, 복잡한 개발·수정만 별도 프로필을 쓴다.

## 3. 실제 CLI를 확인한 뒤 어댑터 연결

`claude-cli`, `gpt-cli`는 사용자 환경에서의 명칭이다. 실행 파일·래퍼의 도움말·버전·출력 형식·종료 코드·인증 상태를 확인한다. 자격증명 값을 출력하거나 Mac 로그인 파일을 VM으로 복사하지 않는다.

공식 제품으로 확인된 경우의 기능 근거:

- Claude Code는 `claude -p`, JSON 출력 및 JSON Schema 기반 결과를 문서화한다. 메타데이터와 실제 구조화 결과를 구분해 읽어야 한다. [공식 문서](https://code.claude.com/docs/en/headless)
- Codex CLI는 `codex exec`, JSONL 이벤트, `--output-schema`, 최종 응답 파일 출력을 문서화한다. JSONL 전체를 VideoSpec JSON으로 취급하지 않는다. [공식 문서](https://learn.chatgpt.com/docs/non-interactive-mode)
- Codex의 ChatGPT 로그인과 API 키 로그인은 다른 이용·과금 경로다. 이 프로젝트는 사용자가 확인한 구독 로그인을 보존한다. [인증](https://learn.chatgpt.com/docs/auth)
- Claude의 `--bare`는 현재 문서상 구독 로그인을 사용하지 않는다. 자동화 시작 시간을 줄이려고 무심코 켜서 API 인증을 요구하는 설계를 하지 않는다. [비대화형 실행](https://code.claude.com/docs/en/headless)

CLI 어댑터가 정규화할 결과는 `status`, `payload`, `provider`, `cliVersion`, `model`, `authMode`, `sessionId`, `usage`, `billingMode`, `durationMs`, `errorCode`다. 토큰·잔여 한도를 제공하지 않으면 `null`/`unknown`으로 남기고 0으로 채우지 않는다. 공급자가 표시하는 예상 API 환산액은 구독 추가 청구액과 별도 필드에 둔다.

프롬프트·근거는 stdin/파일로 전달하고 셸 문자열에 직접 이어 붙이지 않는다. AI는 대본과 장면 데이터만 반환하며 워커가 별도 schema·semantic 검사를 수행한다. 나레이션이 확정된 뒤 프레임 수·자막 시간은 코드로 계산한다. schema 출력 지원이 없는 래퍼는 엄격한 파싱과 제한 수정으로 시험하고, 안정적으로 통과하지 못하면 무인 실행에서 제외한다.

## 4. 구독 운영과 무인 실행 한계

구독 로그인이 가능하다는 사실은 무제한 처리량·영구 인증·추가 과금 없음의 보장이 아니다. 두 구독의 잔여 한도와 해당 계정의 초과 사용 설정을 각각 확인한다. 구독 기반 사용과 API 과금을 혼동하지 않는다. [Claude 비용 관리](https://code.claude.com/docs/en/costs), [Codex 인증](https://learn.chatgpt.com/docs/auth)

| 상황 | 처리 |
|---|---|
| 정상 구독 사용 | 기존 로그인 재사용. 각 작업 시작·종료와 사용량 기록 |
| 한도 도달 | `held_quota`로 보류, 가능한 경우 reset 시각 기록. 무한 재시도 금지 |
| 인증 만료·추가 인증 | `held_auth`. 사람이 정상 로그인 후 재개; 세션 복사·인증 우회 없음 |
| CLI에 사용량 필드 없음 | 호출 수·경과 시간·결과량으로 제한, 토큰은 미확인 표시 |
| 다른 구독으로 전환 | 사전 허용한 경우에만 동일 입력으로 한 번 대체, provider 변경 기록 |
| API 키·추가 크레딧 경로 | 기본 비활성. 승인된 예산·인증 설정 없이는 전환하지 않음 |
| CLI 응답 불명·중단 | 완료 artifact·session 결과를 확인한 뒤 재개, 새 호출을 즉시 중복 시작하지 않음 |

환경에 이미 API 관련 설정이 있더라도 구독에서 유료 API로 조용히 전환되지 않는지 설치 시 확인한다. 확인 항목은 값 노출 없는 인증 방식 판정과 실제 이용 내역이다. 기존 runtime 설정은 이번 기획 수정으로 바꾸지 않는다.

초기 운영은 한 편에 작성 1회, 선택 검토 1회, 수정 1회로 **CLI 시작 최대 3회**다. 하루 3편이면 최대 9회이며 내부 모델 호출 수와는 다르다. 숨은 시스템 프롬프트·도구 루프·추론 때문에 프롬프트 길이가 실제 과금 토큰의 상한이 되지 않는다. 토큰 목표는 경보에 사용하고 실제 중단은 timeout·가능한 turn 한도·허용 도구·공급자 한도로 겹쳐 제어한다.

일상 작업은 새 세션으로 시작하고 필요한 근거만 전달한다. 동일 작업의 실패 복구에만 기존 세션 재개를 허용한다. 전체 이전 대화·프로젝트 문서를 누적하지 않는다. 코드 수정이 필요한 실패는 개발 큐로 보내고 밤새 자기수정·설치·배포를 반복하지 않는다.

## 5. VM 적합성 시험

실제 자원 미확인이므로 아래는 시험 목표이며 Muse 제품 사양이 아니다. 2D 템플릿의 첫 시험 자원으로 4 vCPU·8GiB RAM 이상, 가능하면 16GiB, 여유 디스크 50GiB를 가정하되 실측이 최종 판단이다. GPU 없는 CPU 렌더도 후보이며 3D/WebGL은 별도로 검사한다. Apple 전용 MLX 런타임을 Linux VM에 적용하지 않는다.

| 검사 | 통과 조건 |
|---|---|
| 영속성 | 세션 종료·서비스 재시작 후 큐·음성·출력이 유지됨 |
| 상시성 | 사용자 브라우저·SSH 종료 후에도 워커 실행, idle 종료 정책 확인 |
| CLI 계약 | 두 CLI의 제품·버전·구독 인증·JSON·오류·timeout 동작 기록 |
| 자원 | 고정 영어 45초·1080×1920·30fps 샘플 3회 정상 출력, peak 메모리·임시 디스크 기록 |
| 목표 처리량 | 편당 30분 이내 렌더·01~04시 운영창에서 3편 완료 목표; 실제 p95와 여유 확보 |
| 권한 | 필요한 파일·네트워크만 사용, 미허용 행동은 prompt 대기 대신 명확히 거부/보류 |
| 폰트·음성 | 로컬화한 폰트·에셋으로 렌더, 음성 동기·문자 잘림 확인 |
| 회복 | 재부팅·인증 만료·quota·렌더 실패에서 재개 및 비용 중복 점검 |

VM 렌더가 실패하면 동시성 1·장면 단순화로 1회 재시험한다. 계속 미달이면 Mac 렌더로 분리한다. VM이 영속성·상시성 시험에 실패하면 큐까지 Mac으로 옮기거나 영속 실행 환경을 먼저 마련해야 하며, ‘VM 연결 가능’만으로 새벽 운영 완료를 보장하지 않는다.

Linux VM에서는 사용 가능한 서비스 관리자를 확인해 예약을 구현한다. 스케줄러 종류와 관계없이 워커에 Asia/Seoul 운영창·일일 개수·중복 잠금 검사를 둔다. 플랫폼 자동 재시작이 04시 이후 밀린 3편을 갑자기 실행하지 않도록 한다.

## 6. Mac 렌더 대안의 작업 전달

기본 VM 통합 경로에는 원격 큐 동기화가 없다. Mac 대안을 쓸 때만 VM이 `render_ready` 작업을 임대한다. VM을 큐의 유일한 소유자로 두고 Mac은 전용 pull 워커로 동작한다. 두 장비에서 같은 큐 파일을 동시에 수정하거나 양방향 폴더 동기화를 하지 않는다.

작업 묶음은 spec·음성·폰트·이미지·해시·템플릿 버전·릴리스 ID를 포함한다. 전송 수단은 기존의 인증된 SSH/SFTP 등 확인된 연결을 사용하고 신규 공개 포트·공개 파일 서버를 기본으로 요구하지 않는다. 실제 경로·호스트는 배포 시 정한다.

`leaseId`, `leaseExpiresAt`, `attempt`, `workerId`로 작업을 식별하고 heartbeat·완료 응답을 기록한다. 임대 만료 후 재시도하더라도 이전 attempt의 늦은 결과는 승격하지 않는다. 실행 중복을 완벽하게 막는다고 가정하지 말고 동일 jobKey·입력 해시의 유효한 결과 하나만 수락한다. VM/CLI는 재렌더 때문에 음성을 다시 만들지 않는다.

OS·브라우저·인코더 차이가 있으므로 VM과 Mac MP4의 바이트 동일성을 요구하지 않는다. 같은 템플릿·폰트·입력·버전으로 화면·타이밍을 검수하고 최종 렌더 환경을 manifest에 남긴다. Mac이 꺼져 있으면 작업은 `waiting_renderer`로 남으며 클라우드 유료 렌더로 자동 전환하지 않는다.

## 7. 저장소와 운영 데이터

대상은 [nanbada/ShortsMaker](https://github.com/nanbada/ShortsMaker)다. 2026-10-04 GitHub API 조회에서 공개 저장소, 크기 0, contents 응답 ‘This repository is empty.’를 확인했다. 로컬 폴더에도 `.git`이 없다. 현재 기획 문서가 GitHub에 저장되었다고 간주하지 않는다.

후속 구현 시 코드·스키마·템플릿·프롬프트·작은 비민감 fixture·기획을 Git으로 관리한다. 음성·화면 캡처·영상·작업 큐·로그·세션·인증은 운영 디스크에 둔다. 특히 공개 저장소에 `.env`, CLI 로그인 파일, 실제 사용자 대본·미디어·미가공 응답 로그를 넣지 않는다.

검증한 릴리스의 commit ID와 lockfile로 실행 버전을 고정한다. 매 새벽 main을 무조건 pull해 설치·업데이트하지 않는다. 배포 시 작업 큐를 비운 뒤 검증한 버전으로 전환하고, 문제가 있으면 이전 배포본으로 돌아가되 입력·출력·상태를 삭제하지 않는다. 커밋·푸시·VM 배포는 이번 문서 수정 범위에 포함하지 않았다.

## 8. 구현 순서

1. 실제 VM·CLI 정보와 구독/초과 사용 조건을 기록하고 비밀을 출력하지 않는 사전 점검을 만든다.
2. 한 CLI로 준비된 근거를 구조화 대본으로 출력하는 감독하의 1편을 만든다. 다른 CLI는 선택 검토만 시험한다.
3. 관리형 음성 1개와 렌더러 1개를 연결하고 VM에서 후보 MP4·SRT·QA·비용 보고서를 완료한다.
