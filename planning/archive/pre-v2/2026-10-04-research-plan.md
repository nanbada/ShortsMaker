> 상태: v2 이전 조사 이력. [기획 v2](../../2026-10-04-claude-code-render-plan-v2.md)로 대체되었다. 아래 VM 우선·영어 기본·야간 운영 및 저장소 상태는 당시 기록이며 현재 실행 지시가 아니다. 현재 상태는 [README](../../../README.md)를 따른다.

기준일: 2026-10-04, Asia/Seoul. 개정: 로컬 전용 조건 해제, Muse AI VM의 Claude/GPT CLI 운영 반영. 상태: 조사·기획 완료, 구현·렌더·음성 청취·야간 운영 실험 전.

## 1. 권고와 적용 범위

**Muse AI VM에서 Claude/GPT로 대본·장면 데이터를 만들고, 검증된 템플릿과 확정 음성을 조합하는 제작 워커를 운영한다.** VM에서 2D 영상 렌더까지 완료하는 것을 기본안으로 두고, 성능·비용 시험 미달 시에만 Mac 렌더로 분리한다. 하루 1편으로 시작해 야간 1~3편을 생성하고, 아침에 게시 가능 여부를 검수한다. 영어가 기본이며 다른 언어는 요청한 버전만 생성한다. 로컬 LLM 설치·유료 렌더 서비스·생성형 영상·매일 새로운 코드 작성은 필수 구성요소가 아니다.

사용자가 Muse VM에 `claude-cli`, `gpt-cli`가 연결되어 있다고 알려 주었다. 추가로 구독 로그인이라고 확인했다. 실제 제품·버전·구독 한도·초과 과금·VM 자원은 아직 조회하지 않았다. 특정 래퍼를 공식 Claude Code 또는 Codex CLI로 단정하지 않는다. 선택 근거와 실행 계약은 [Muse VM 실행 설계](remote-execution.md)에 둔다.

핵심 선택은 다음과 같다. 모두 요구에 따른 설계 제안이며 속도·품질의 실측 결과가 아니다.

## 2. 코드 렌더링의 실용성

AI는 대본·구도·자료 선택을 돕고, 렌더러는 시간별로 텍스트·이미지·도표·화면을 그려 영상으로 인코딩한다. 일상 생산에서는 AI가 임의 코드를 실행하게 하기보다 허용된 장면과 속성을 담은 데이터만 출력하도록 한다. 템플릿을 만드는 개발 과정과 매일 데이터를 채우는 운영 과정을 분리하는 것이 비용과 실패율을 낮추는 핵심이다.

| 영상 유형 | 적합도 | 실제 필요한 재료·작업 | 초기 운영 |
|---|---|---|---|
| 제품 UI 설명·계산 예시 | 높음 | 실제 화면, 입력값, 결과 검증, 확대·강조 | 첫 파일럿 |
| 비교·리스트·교육 설명 | 높음 | 직접 쓴 해설, 근거, 표·도표 | 첫 파일럿 |
| 뉴스 요약 | 중간 | 시의성·출처 확인과 정정 처리 | 상시 콘텐츠 안정화 뒤 추가 |
| 삽화에 카메라·레이어 움직임 | 중간~높음 | 권리 확인된 그림, 레이어 분리, 간단한 동작 | 두 번째 시각 템플릿 |
| 미니어처 3D·캐릭터 이야기 | 중간 | 3D 장면·카메라·일관된 캐릭터, 추가 QA | 정기 생산과 분리한 실험 |
| 실사 인물 연기·복잡한 물리 동작 | 낮음 | 촬영·스톡·생성형 영상 등 다른 재료 | 초기 범위 제외 |

코드 렌더링은 새로운 발명이라기보다 기존 프로그래밍 영상 제작에 AI 코딩과 제작 워크플로가 결합한 흐름이다. 최근 agent용 제작 지원은 유용하지만, 자동으로 좋은 대본·연출·사실 정확성을 보장하지는 않는다. 생성형 영상 API를 쓰지 않으면 그 항목의 비용은 없지만 텍스트 모델, 음성, 이미지, 라이선스, 저장 공간, 전기, 수정 노동은 남는다.

### 제공된 사례의 활용 범위

1. **Promptwhat 사례:** 사용자 제공 설명의 ‘실제 화면 확보 → 음성 확정 → 11컷 구성 → 자막’ 순서를 채택한다. 11컷과 90분은 해당 사례의 진술이지 본 프로젝트 처리시간 기준이 아니다. 45초 영상은 우선 6~9컷으로 시작한다. 계산기 결과는 동일 입력을 별도로 계산해 대조하고 화면 캡처 시점도 기록한다.
2. **akakuma0219 사례:** 일러스트에 움직임을 주는 방향은 채택할 수 있다. 한 장의 이미지를 평면으로 배치하고 카메라를 이동하는 것과 실제 3D 공간·가려진 면을 만드는 것은 다른 작업이다. 먼저 2~4개 레이어의 2.5D 템플릿, 이후 필요할 때 Three.js를 시험한다. 게시글의 모델 명칭이나 한 번의 지시로 완성했다는 설명을 재현성 근거로 삼지 않는다.

두 X 원문은 접근 실패했다. 연결된 ChatGPT 대화는 로그인 화면만 읽혔다. 따라서 사용자가 붙여 준 설명과 프로젝트 파일을 참고했으며 링크 원문을 읽었다고 주장하지 않는다. [사례 1](https://x.com/Promptwhat/status/2106364893679018098), [사례 2](https://x.com/akakuma0219/status/2105990418886480092)

## 3. 렌더링 도구 선택

| 도구 | 장점 | 비용·운영 제약 | 판단 |
|---|---|---|---|
| Remotion | React 컴포넌트·props로 반복 장면 구성 | 무료 자격 확인 필요; 프레임 기준 애니메이션과 브라우저 관리 필요 | 개인·소규모 무료 자격이면 우선 |
| HyperFrames | HTML/CSS, seek 가능한 애니메이션, CLI 검사·출력, Apache-2.0 | 현재 설치 버전과 실제 무인 렌더·오디오·폰트 동작 검증 필요 | 유료 Remotion 비용 회피 또는 HTML 자산 중심이면 우선 |
| FFmpeg 중심 | 기존 이미지·영상의 결합과 인코딩에 적합 | 복잡한 문자 배치·디자인 변경을 filter만으로 관리하기 어려움 | 공통 출력·검사 도구. 단순 슬라이드만이면 단독도 가능 |
| Motion Canvas | TypeScript 기반 설명용 벡터 애니메이션·음성 동기화 | 주력 편집기/코드 방식의 적합성 시험 필요 | 수학·교육 애니메이션 특화 후보 |
| Three.js | 미니어처·공간·카메라 표현 | 자체적으로 전체 제작 큐·오디오·자막·인코딩을 해결하지 않음 | 선택한 엔진 내부의 후속 장면 유형 |
| Blender | 실제 3D 장면, 백그라운드 렌더 | 에셋·조명 제작과 렌더 비용 증가 | 3D가 채널 차별화의 핵심일 때만 |

근거: [Remotion 데이터 처리](https://www.remotion.dev/docs/parameterized-rendering), [HyperFrames 공식 저장소](https://github.com/heygen-com/hyperframes), [FFmpeg 필터](https://ffmpeg.org/ffmpeg-filters.html), [Motion Canvas](https://motioncanvas.io/docs/), [Three.js](https://threejs.org/manual/en/creating-a-scene.html), [Blender CLI](https://docs.blender.org/manual/en/latest/advanced/command_line/render.html).

Remotion은 개인 및 3인 이하 조직 등 무료 대상에게 상업 사용·자동화를 허용한다. 무료 대상이 아닌 자동화는 Automators의 월 최소 $100이 중요한 비용이다. 개발자 1명이라는 이유만으로 조직 전체의 무료 자격을 단정하지 않는다. 이 프로젝트에서는 조직 관계를 아직 확인하지 않았다. [가격](https://www.remotion.dev/docs/license/pricing), [FAQ](https://www.remotion.dev/docs/license/faq)

**엔진 시험을 최대 2개, 1~2개 개발일로 제한한다.** 동일한 영어 45초 음성·이미지·폰트로 6컷을 만들고, 제목 변경·이미지 교체·음성 길이 변경을 수행한다. 냉간/재실행 각각 3회에서 총 소요시간, 최대 메모리, 임시 디스크, 수정 시간, 오류 수를 기록한다. 임의 프레임 탐색, 자막 동기, 네트워크 없는 렌더가 통과 조건이다. 둘 다 통과하고 무료 자격이면 Remotion을 선택한다. 유료 대상이고 추가 비용 최소화가 우선이면 HyperFrames를 선택한다. 특정 엔진의 디자인 품질이나 속도 우위를 미리 가정하지 않는다.

하나만 통과하면 그 엔진의 비용이 허용 범위인지 확인해 선택한다. 둘 다 실패하면 FFmpeg 기반 단순 장면 합성으로 파일럿 범위를 줄이고 복잡한 연출을 연기한다. 두 엔진을 동시에 제품화하지 않는다.

## 4. 음성 우선 제작과 다국어

기본 언어는 `en-US`. 대사, 지문, 화면 문구, 자막을 영어로 만든다. 운영 문서·오류 요약은 한국어로 제공한다. `ko-KR`, `ja-JP`, `zh-CN`은 명시 요청할 때 별도 작업으로 생성한다. 번체·광둥어 요청은 `zh-TW`·`yue` 등 범위를 별도로 정하고 보통화와 동일 취급하지 않는다.

| 후보 | 역할 | 확인한 사실 | 미확인·주의 |
|---|---|---|---|
| Kokoro-82M | 영어 자체 실행 비교 후보 | 82M 규모, Apache 계열 라이선스 모델·추론 코드; 영어·일본어·중국어 경로 | 공식 기본 언어 목록에 한국어 없음. VM/Mac 음질·속도 미측정 |
| Qwen3-TTS | 한국어 포함 로컬 다국어 후속 후보 | 0.6B/1.7B, 영어·한·일·중 포함 10언어, Apache-2.0 | 더 큰 모델의 메모리·발음·속도 검증 필요 |
| MLX-Audio | Apple Silicon 실행 후보 | Kokoro·Qwen 계열 실행 예제 제공 | 원 모델 공식 구현과 별개 프로젝트. 변환 가중치·라이선스·버전을 따로 고정 |
| Google Neural2 | 관리형 저비용 비교 후보 | 문자 과금; 지원 음성과 기능은 선택 모델별 확인 | 단어 타임스탬프를 자동 제공한다고 가정하지 않음 |
| Azure Speech | 기존 설계의 대안 유지 | 기존 문서가 SSML·WordBoundary 기반으로 설계 | 이번 영어 최소비용 설계에서 무조건 기본값으로 고정할 근거 없음 |
| ElevenLabs | 감정·자연스러움이 중요한 선택 옵션 | 유료 상업 조건, v4 모델 문서 확인 | v4는 Text to Dialogue 경로. 기존 TTS 타임스탬프 API 호환을 추정하지 않음 |

근거: [Kokoro 모델 카드](https://huggingface.co/hexgrad/Kokoro-82M), [언어 목록](https://github.com/hexgrad/kokoro), [Qwen3-TTS](https://github.com/QwenLM/Qwen3-TTS), [MLX-Audio](https://github.com/Blaizzy/mlx-audio), [Google SSML](https://docs.cloud.google.com/text-to-speech/docs/ssml), [ElevenLabs 모델](https://elevenlabs.io/docs/overview/models).

같은 영어 대본 10개로 Kokoro와 관리형 음성 1개를 비교한다. 숫자·통화·날짜·약어·고유명사·빠른 구문을 포함하고, 합성 시간보다 수정 횟수와 ‘바로 쓸 수 있는 음성’ 비율을 우선 평가한다. 로컬 음성 때문에 월 1시간 이상 추가 검수가 생긴다면, 월 수 달러의 관리형 음성이 총비용에서 유리할 수 있다. 이는 비교 기준 제안이며 실제 결과는 아니다.

제작 순서:

1. 근거와 핵심 메시지를 확인하고 영어 대본을 확정한다. 45초는 약 90~110단어로 시작하되 실제 음성 길이로 판단한다.
2. `spokenText`와 화면 문구를 분리한다. 지문은 음성에 그대로 읽히지 않도록 별도 필드로 저장한다.
3. 최종 음성을 생성·저장하고 실제 길이를 측정한다. 음성·대본·목소리 설정 해시를 고정한다.
4. 문장 또는 짧은 구절 단위로 장면을 배치한다. 초기 로컬 음성은 구절 단위 합성 후 파일 길이와 연결 위치를 이용해 자막 구간을 만든다. 이 방식은 단어 단위 정렬이 아니며 문장 간 억양이 부자연스러우면 전체 음성+정렬 방식으로 전환한다.
5. 전체 음성에 native timing이 있으면 사용하고, 없으면 forced alignment를 별도 시험한다. 자동 음성 인식 결과를 원 대본 대신 진실로 취급하지 않는다. 속도 광고를 M3 성능으로 옮기지 않는다. [WhisperX](https://github.com/m-bain/whisperX)
6. 번역 버전은 대본 현지화 → 새 음성 → 새 길이 → 컷·자막 재배치 순으로 제작한다. 영어 타임라인에 번역 자막만 억지로 맞추지 않는다. 숫자·단위·화면 UI 언어·글꼴·줄바꿈도 다시 검사한다.

한 원본을 네 언어로 만들면 산출물은 네 편이다. 기본 하루 1~3개는 **전체 언어를 합한 최종 파일 수**이며 다국어 자동 증식을 하지 않는다.

## 5. VM 우선 제작 구조

`주제 큐 → 근거 수집 → 대본·장면 계획 → 음성 확정 → VideoSpec → 자동 검사 → 저해상도 미리보기 → 고해상도 후보 파일 → 사람 검수 → 게시용 파일`

| 단계 | AI 역할 | 일반 코드의 역할 | 산출물 |
|---|---|---|---|
| 수집 | 자료 선별·요약 | 허용 출처만 수집, 날짜·URL·해시 기록 | claim-source 묶음 |
| 대본 | 훅·설명·마무리와 장면 의도 작성 | 길이·금지 표현·필수 근거 검사 | script, storyboard data |
| 음성 | 필요할 때 발음 표기 제안 | TTS 1개 호출 또는 로컬 합성·캐시 | narration, timing |
| 편집 계획 | 허용 장면·강조 위치 선택 | 템플릿 선택, 프레임 계산, 계약 검사 | VideoSpec |
| 출력 | 일상 경로에는 불필요 | 브라우저 프레임 렌더·인코딩 | MP4, SRT, thumbnail |
| 검수 | 선택적 대표 이미지 평가 | overflow, 길이, 파일·음량·해시 검사 | QA report, manifest |

큐와 상태는 Muse VM의 영속 디스크에 파일로 시작한다. `jobs/<id>/`에 입력과 상태, `out/<id>/<run-id>/`에 결과를 저장한다. 워커 한 개와 잠금으로 중복 실행을 막는다. AI CLI는 워커가 단계별로 호출하고 종료하며 스케줄·재시도·게시 권한을 소유하지 않는다. Mac 렌더를 쓰는 경우 VM만 큐의 원본을 소유하고 작업 임대·결과 해시로 중복을 차단한다. 세부 계약은 [실행 설계](remote-execution.md)에 둔다. 새 SaaS, 별도 웹 편집기, 다중 에이전트 서버, 벡터 DB는 초기 요구에 넣지 않는다.

웹 화면 캡처는 처음에는 수동으로 준비한 파일을 입력한다. 다음 단계에서 검증한 사이트별 Playwright 절차를 추가한다. 임의 사이트 탐색 에이전트를 매일 돌리기보다 URL·뷰포트·입력값·버튼·기대 결과를 고정한 캡처 절차가 재현하기 쉽다. 로그인 정보·개인정보가 있는 화면은 별도 마스킹 대상이다. 최종 렌더는 저장된 에셋만 읽는다.

수집한 웹 문구는 참고 데이터이며 실행 지시가 아니다. AI가 만든 임의 JavaScript/셸 명령을 운영 워커에서 실행하지 않는다. 렌더링 코드와 의존성은 낮에 검증한 버전으로 고정한다.

## 6. 야간 자동화와 검수 경계

목표는 무인 **제작**이다. 매 단계에서 사람을 기다리는 기존 흐름은 새벽 운영과 맞지 않으므로 자동 기술 검사와 사람의 게시 검수를 구분한다.

- 첫 3편은 감독하에 생성하고 음성·자막·화면 전체를 검수한다.
- 통과한 템플릿과 승인한 주제 목록으로 야간 후보 영상을 만든다. 후보 MP4 생성에는 별도 사람 승인을 기다리지 않는다.
- 새로운 템플릿, 근거 불명, 권리 불명, 민감한 주장, 정렬 실패는 `held`로 격리한다. 정상 작업은 계속 진행한다.
- 후보 파일은 `needs_review` 상태다. 사람이 확인한 정확한 입력·출력 해시에만 `approved`를 부여한다. 수정되면 승인은 만료된다.
- 내용·화면 QA를 통과한 것과 수익화·성과가 보장되는 것은 다르다. 초기 게시 자체는 수동이다.

VM의 OS와 서비스 관리자를 확인해 예약 실행을 선택한다. Linux이면 `systemd timer`와 단일 서비스가 후보이며, Muse 자체 예약 기능은 영속성·재시작·중복 실행 조건을 확인한 경우 사용한다. 대화창이나 SSH 연결이 끊겨도 진행되는지 시험한다. Mac 대안은 `launchd`를 쓰되 수면·전원 때문에 야간 완료를 보장할 수 없으므로 예비 산출물을 준비한다. 이번 작업은 VM에 접속하거나 예약 설정을 설치하지 않았다. [Apple 예약 작업 문서](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/ScheduledJobs.html)

상세 일정, 재시도, 저장 공간, 비용 한도는 [운영 설계](operations-budget.md)에 둔다.

## 7. 영상 규격과 채널 가치

공통 초기 프로필: 1080×1920, 9:16, 30fps, H.264/yuv420p, AAC 48kHz·128kbps, MP4 faststart. 길이 기본 30~60초, 프로젝트 상한 90초는 유지 후보다. 8Mbps는 저장 용량 계산용 시작값이지 필수 플랫폼 규격이 아니다. 실제 화질을 확인해 조정한다.

YouTube Shorts는 정사각형·세로 영상 최대 3분을 다루므로 프로젝트의 60/90초는 제품 선택이다. 1분 초과 영상의 Content ID 주장 관련 제한도 고려해 초기에는 직접 확보한 음성과 필요한 효과음만 사용한다. [YouTube Shorts](https://support.google.com/youtube/answer/15424877)

Instagram 공식 API 문서는 9:16 권장, H.264/HEVC·AAC 등의 요건을 안내한다. 자동 게시 단계에는 professional account, 권한, 업로드 방식, 컨테이너 상태 확인이 추가된다. URL로 넘기는 경로는 외부 접근 가능한 미디어 위치가 필요하므로 로컬 파일 생성만으로 자동 게시가 끝나지 않는다. 게시 한도 수치는 문서·경로 간 차이가 있어 현재 계정의 API 응답으로 확인해야 한다. [Meta 규격](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/media/), [게시 가이드](https://developers.facebook.com/docs/instagram-api/guides/content-publishing)

수익화를 원한다면 매 영상에 직접 검증한 예시, 독자적 해설 또는 분명한 교육·오락 가치를 넣는다. YouTube는 반복·대량 생산되고 차별적 가치가 낮은 콘텐츠를 수익화 부적격으로 설명한다. 템플릿을 사용한다는 사실만으로 결과를 단정할 수 없으며 영상의 실질 내용이 중요하다. 현실적으로 보이는 합성·변조 장면은 공개 표시 대상 여부를 검토한다. [수익화 정책](https://support.google.com/youtube/answer/1311392), [합성 콘텐츠 표시](https://support.google.com/youtube/answer/14328491)

자동 QA는 다음을 검사한다: 필수 에셋·권리 정보, 허용 경로, 텍스트 잘림, 자막 2줄 이내, 컷 경계, 음성 잘림·무음 이상, 최종 길이, 인코딩 규격. -16 LUFS와 true peak ≤-1dBTP, 자막 동기 150ms 이내는 내부 목표다. 글자 크기·safe area는 플랫폼 공식 보장값이 아니라 실제 모바일 화면으로 보정할 값이다. 사람은 발음, 사실, 전달력, 화면 내 작은 글씨와 플랫폼 UI 가림을 확인한다.

## 8. 기존 자료와 새 요구의 차이

기존 파일을 덮어쓰거나 이미 구현된 것으로 취급하지 않는다. 아래는 후속 구현 시 반영할 변경 목록이다.

| 기존 파일·내용 | 새 기획의 처리 | 구현 전 완료 조건 |
|---|---|---|
| `video-spec.schema.json`: `language.const = ko-KR` | 명시적 언어 목록, 기본 생성 `en-US` | 계약 버전을 올리고 기존 한국어 예시도 보존·검증 |

| `02-PRD.md`: 한국어 P0, Azure 기본 | 영어 P0, 로컬/관리형 음성 청취 후 하나 선택 | 영어 fixture와 요청 언어별 검사 추가 |
| `02-PRD.md`: 최종 렌더 전 사람 검수 | 무인 후보 렌더와 게시 승인을 분리 | 기술 QA 통과로 후보 생성, `approved` 전 게시 차단 |
| `03-development-plan.md`: 수동 CLI 중심 | 큐·예약·재시작·한도·일일 결과 추가 | 기상 지연·강제 종료·중복 실행 시험 |
| `04-agent-handoff.md`: 여러 도구 역할 분담 | VM Claude 작성 기본 후보, GPT 선택 검토·개발 지원 | 매 영상 다중 모델 릴레이 제거; 실제 CLI 기능·사용량 확인 |

현재 폴더는 Git 저장소가 아니며, 실제 렌더러나 큐 워커가 없다. 대상 [GitHub 저장소](https://github.com/nanbada/ShortsMaker)는 조회 시 공개된 빈 저장소였다. 코드·템플릿·기획의 관리 위치로 계획에 반영하되 원본 미디어·인증·작업 로그는 공개 저장소에 넣지 않는다. 포함된 Python 검증기는 계약 예시용이고 실제 에셋·음성·시각 QA를 확인하지 않는다. 이번 작업에서 기존 스키마·검증기·예시 파일을 수정하지 않았다.

## 9. 단계별 실행 계획과 성공 기준

아래 기간은 단일 구현 담당자 기준의 계획 추정이며 견적·보장 일정이 아니다. 후속 구현 요청 시 시작한다.

| 단계 | 추정 | 결과 | 종료 기준 |
|---|---|---|---|
| P0 비교 | 1~2 개발일 | VM/CLI 기능 확인, 엔진 2개·음성 2개 샘플, 라이선스 판정 | CLI 무인 종료·구조화 출력·과금 확인, VM 렌더 실측 후 실행 위치 확정 |
| P1 첫 제작 | 3~5 개발일 | 한 엔진, 3개 템플릿, 영어 계약, 음성·자막·MP4 | 내용만 바꿔 3편 완성, 재렌더 TTS 호출 0 |
| P2 야간 운영 | 2~4 개발일 | VM 큐·잠금·재개·CLI 어댑터·비용 원장·일일 결과 | 7일간 하루 1편, 연결 종료·인증 만료·사용 한도 시험, 중복 과금·덮어쓰기 0 |
| P3 확대 | 운영 1~2주 | 하루 3편·요청 다국어·검증한 캡처 절차 | 후보 제작 성공률 95% 목표, 사람 검수 중앙값 5분/편 목표 |
| P4 선택 확장 | 필요 확인 후 | 2.5D/3D, 선택 이미지 생성, 게시 연동 | 기존 방식보다 시청 성과·수정 시간 개선 근거 확보 |

95%는 목표이며 7편만으로 안정성을 증명하지 않는다. 20건 이상 누적 표본에서 품질·실패 원인을 함께 판단한다. 렌더 30분/편 이내와 야간 4시간 안 3편 완료를 초기 운영 목표로 삼고 실측으로 수정한다. 실패하면 하드웨어 구매보다 장면 복잡도·해상도 미리보기·동시성·에셋 수부터 줄인다.

초기 템플릿은 ‘화면 기능 3단계’, ‘근거 있는 비교’, ‘짧은 설명+도표’ 3종이다. 매일 3종을 모두 강제하지 않는다. 주 1회는 완주율·평균 시청 시간·초반 이탈·검수 시간·합격 1편당 비용을 함께 보고 주제와 구성만 조정한다. 자동으로 많이 만드는 것 자체를 성공 지표로 삼지 않는다.

후속 구현 전에 확정할 최소 정보는 **콘텐츠 주제·권리 범위, 개인/조직 사용 관계, 유료 호출 허용액, Muse VM 자원·영속성·CLI 제품과 구독 한도**이다. 현재 권고는 기존 VM·기존 Claude/GPT 이용권 재사용, 영어 정보형 영상, 종량·초과 과금 월 $10 이내라는 가정이다. VM·구독 총비용은 실제 계약으로 별도 확정한다. VM 성능 미달 때만 Mac 실행 조건을 추가 확인한다.
